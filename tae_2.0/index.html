Ch.1 — Introduction to Test Automation
3 pts (7%) Easy · All K2 3 Questions
💡 What Is Test Automation?
💻Using software tools to run tests, check results, and generate reports automatically
🔍Interacts with desktop, mobile, API, network, and protocol-level systems
📦Can work without a UI — some tests don't need a graphical interface
✅ Benefits of Automation
⚡
Speed & Scale
Run far more tests per build than manual teams. Execute faster, more consistently.
🛠
Impossible Tests
Parallel execution across environments, remote testing, split-second timing tests.
🎯
Consistency
Eliminates human error from fatigue. Tests run the same way every time.
⚠ Challenges & Limits
Challenges
💰High upfront costs: licenses, infra, training, hiring
🔄Continuous maintenance required
🚨Poorly designed scripts can introduce new defects
Hard Limits
🗙Some tests simply can't be automated
🔍Only checks what you explicitly programmed
🔎Can't verify quality attributes that aren't machine-checkable
🛠 Automation in Dev Models
📝
Waterfall
Phases: req → design → dev → test → maintain. Automation enters during/after dev.
➔
📝
V-Model
Dev stages linked to matching test levels. Frameworks set up per test level.
➔
🚀
Agile
Richest automation opportunities. In-sprint automation, CI pipelines, pair programming.
🔧 Choosing Tools
🎯Start with what you're testing and your goals
👥Consider team skills — low-code if testers aren't strong coders
💰Evaluate long-term: scalability, cost, language alignment with SUT
🔗Commercial vs open-source — decide based on total cost of ownership

🎯 Key Takeaway

Ch.1 is your easiest 3 points. Master it first for early exam confidence. Target 90–100%.
Ch.2 — Preparing for Test Automation
9 pts (21%) Medium · K2 + K4 5 Questions

⚠ Two K4 Questions Worth 3 Points Each

This chapter mixes K2 recall with high-value K4 questions. Deep understanding is critical. Do not spend excessive exam time here — master it during study.
🛠 Testability by Design
🔑Testability must be baked in from the start, not tacked on later
📄Usually handled by software architect + automation engineers
👁
Observability
Interfaces that let you see what's happening inside the system
🔧
Controllability
Interfaces to drive the system: UI, APIs, TCP/IP, USB, signals
📄
Architecture Transparency
Clear docs laying out components and interfaces at every test level
🏠 Test Environments
💻 Local Dev Environment
White-box testing, component/GUI/API tests, earliest defect detection
📦 Build Environment
CI/CD agent runs low-level tests + static analysis. Verifies build correctness.
🔀 Integration Environment
Fully integrated release candidate. Black-box only. Monitoring becomes important.
🚀 Preproduction
Mirrors production. Non-functional testing (performance). UAT by stakeholders.
🌐 Production
Real users. Canary releases, blue/green deployment, A/B testing. Monitoring critical.
📋 System Analysis Requirements
📄Which test activities to automate (management, design, generation, execution)
🎯Which test levels and types need support
👥Which roles and skill sets need support
📦Which systems/products/families need support (scope & lifespan)
📊Test data availability and quality
🔍Ways to emulate hard-to-reach scenarios (third-party apps)
📋 Tool Evaluation Checklist
Language/IDE
Tool's language, IDE tooling, developer familiarity
Configuration
Environment support, run configs, dynamic/static values
Test Data
Internal data mgmt, central repo integration, version control
Reporting
Must align with project reporting requirements
Integration
CI/CD, task tracking, test management, reporting tools
Scalability
Architecture expandability, maintainability, modifiability

Ch.3 — Test Automation Architecture
10 pts (23%) Hard · K3 Precision 6 Questions

⚠ Precision Is Everything

Short chapter, but every word matters. Classic mistake: skimming over it because it's short. Every distinction in the syllabus is tested.
🛠 The Big Picture
💡Test automation architecture is the blueprint for how automated tests connect to everything else in the project
💻
System Under Test
The system being tested
➔
📄
Project Management
Project tracking & planning tools
➔
📋
Test Management
Test cases, results, reporting
➔
🔄
CI/CD & Version Control
Pipelines, repos, deployments
📚 Core Capabilities
📄
Test Generation
Create tests automatically from models (optional)
✎
Test Definition
Write and organize test cases
▶
Test Execution
Run tests and log results
🔗
Test Adaptation
Connect to SUT via APIs and interfaces
📚 Three-Layer Framework
📌 Test Scripts Layer (Top)
Contains actual test cases. Calls business logic but never jumps directly to core libraries.
📌 Business Logic Layer (Middle)
System-specific code. Sets up configurations and connects to your application.
📌 Core Libraries Layer (Bottom)
Reusable, project-agnostic code. Shared across teams and applications.
🛠 Automation Approaches
🎥
Capture/Playback
Records clicks. Good for demos. Hard to maintain.
✎
Linear Scripting
Step-by-step scripts. Simple but messy at scale.
🛠
Structured Scripting
Reusable components. Most real-world projects.
🚀
TDD
Write tests before code. Red-green-refactor cycle.
📊
Data-Driven
Same test, different data from files/DBs. Efficient variations.
💡
Keyword-Driven
Tables of keywords anyone can read. Complex to set up.
🤝
BDD
Given-When-Then natural language. Collaboration-focused.
💡 Design Patterns
🛠Facade Pattern: Hides complexity, shows testers only what they need
🔒Singleton Pattern: Ensures only one connection to SUT at a time
🏠Page Object Model: All page info in one place. Changes only update once.
🔄Flow Model Pattern: Extra layer on top of page objects for better reusability
🚨 Common Ch.3 Traps
⚠ Correct, but at the wrong layer
Answer is valid but belongs to a different framework layer. ISTQB is strict about layer responsibility.
⚠ Sounds practical, but breaks maintainability
Mirrors real-world automation but violates ISTQB principles. ISTQB always prioritizes long-term cost reduction.
⚠ Tool-first instead of architecture-first
Focuses on tools rather than goals. ISTQB prefers tool-agnostic architecture with defined interfaces.
⚠ Framework types that sound interchangeable
Reuse of test logic → modular. Externalizing test data → data-driven. Keywords for non-technical users → keyword-driven.

🎯 Elimination Checklist

When stuck: Does this separate concerns? Reduce future maintenance? Scale without rewriting? Fit the team? Avoid tool lock-in? Eliminate if it fails 2+.

Ch.5 — Deployment Strategies
8 pts (19%) Medium · K2/K3 6 Questions

⚠ Syllabus, Not Company Practice

How ISTQB wants you to do things is often different from how your company does it. Study the syllabus, not your daily habits.
🔄 Test Levels in Pipelines
🛠 Configuration Tests
Run during build of test automation project. Check file paths, existence of files — "testing the tests"
📌 Component Tests
Execute during build. Test library classes, web components. Quality gates — pipeline stops on fail.
🔀 Component Integration Tests
Run alongside component tests in CI. Test how low-level components work together.
🌐 System Tests
Integrated into continuous deployment. Final quality gate before delivery.
🔀 System Integration Tests
Part of continuous delivery. Verify separately-developed system components work together.
🎯 Two Pipeline Approaches
✅
Tests as Part of Deployment
✅Fail = auto rollback
🚨Rerun requires redeployment
🚀
Tests as Separate Pipeline
✅Multiple test suites, different code
🚨No auto rollback, manual intervention
🔧 Configuration Management
🌐
Environment Config
URLs, credentials, settings per environment. Store with test code or shared repo.
📊
Test Data
Varies by env, release, features. Small: store with tests. Large: dedicated TDM system.
📄
Test Suites
Smoke, regression, feature-specific. Different suites run at different levels.
🛠 Release Management
🚫
Feature Toggles
Define active features per release/env. Skip tests for unavailable features.
📅
Version-Matched Releases
Test code released alongside SUT with same version number. Tags or branches in VCS.
🔀 Contract Testing
📝Verifies services communicate properly per agreed rules
🔗Captures interactions in a "contract" — verifies both parties stick to it
✅Catches defects earlier, especially in microservices
Consumer-Driven
Consumer sets expectations for how provider responds
Provider-Driven
Provider creates contract showing how services operate

💡 The Secret Trick

Questions almost always come down to one thing: Who is the stakeholder, and what do they need to know? Identify the audience (management vs technical), purpose (decision vs execution), and level (summary vs detail) and the answer becomes obvious.
📊 Data Collection Sources
🌐
SUT Logs

🛠
Framework Logs

📈
Production & Perf
Production monitoring, load/stress/spike test logs
📸
Visual Records
Screenshots during execution, screen recordings
👥 Stakeholder Reports
💼
Management
Architects, PMs, test managers. Trends, pass-fail ratios, automation reliability.
Summary level
Charts showing test count changes, overall pass/fail trends, reliability metrics.
📄
Operational
Product owners, BAs. Product use metrics, business impact of results.
💻
Technical
Devs, testers, TA engineers. Root causes, specific failure info, lower-level details.

Ch.7 — Verifying the TA Solution
8 pts (19%) Easy · Mostly K2 6 Questions
🛠 Installation Best Practices
✅Automated install from repo > manual setup
🔗Guarantees consistent versions across environments
🔄Upgrades manageable through repository
📄Same process as standard development tools
🔄 Setup & Teardown Repeatability

🎯 Success Looks Like

Building and rebuilding your test automation produces identical results across multiple environments.
🛠 Framework Verification
✅
Functional Testing
Do components work? Test object verification against wide range of object types.
📈
Non-Functional
Performance degradation, resource utilization (memory leaks), interoperability.
🔍
Accuracy
Logs produce accurate info. Reports accurately reflect system behavior.
📋 Test Suite Composition
✅All test cases have expected results
✅Test data is present
✅Correct framework version
✅Correct SUT version
🔄 Repeatability & Intrusiveness
🔄
Test Repeatability
Same test should always give same result. Flaky tests: remove from active suite and analyze separately.
🚨
Tool Intrusiveness
Close integration can cause different behavior vs manual testing. High intrusion = false failures = lost confidence.
📄 Static Analysis
🔍Finds vulnerabilities and defects without executing
🔒Applies to both SUT and test automation framework
⚠Example: password in plaintext in test scripts = security vulnerability
🚀Runs early in pipelines for immediate feedback (DevSecOps)

🎯 Key Takeaway

Ch.7 = test the tests. Aim for 100%. Mostly K2 with some K3 verification scenarios.
Ch.8 — Continuous Improvement
13 pts (30%) Hard · K3/K4 6 Questions

⚠ Largest Chapter on the Exam

13 of 66 total points. Do not treat as optional. You may arrive here still needing 3+ points to pass.
📈 Finding Improvements Through Data
📊
Test Histograms
Visual reports showing trends. Identify flaky tests, select tests for refactoring.
🤖
AI Self-Healing Tests
ML detects changed UI locators, identifies new selectors, auto-fixes tests. Speeds maintenance.
🛠 Scripting Improvements
🚀Upgrade from linear → data-driven or keyword-driven for new tests
🔄Consolidate overlapping tests into reusable library functions
🛡Establish failure recovery — auto-reboot SUT where feasible
🕑 Wait Mechanism Optimization
🚨 Hard-coded Waits (Worst)
Wait X milliseconds. Unpredictable response times. Can cause many defects.
💡 Dynamic Polling (Better)
Check if state changed. Waits only as long as needed. Must include timeouts.
✅ Event Subscription (Best)
Subscribe to system events. Most reliable. Requires scripting language support + timeout.
⚡ Execution Improvements
🔄Test concurrently on different environments
✎Split regression suites into timed batches
🔍Analyze coverage for duplication — removing reduces execution time
🚀Run batch jobs in parallel for CI/CD pipelines
🕑Schedule automated jobs at specific times (e.g. every morning)
🛠 Architecture & Framework Updates
🛠
Architecture Changes
Update SUT architecture for testability. Add APIs for testing early — adding later is expensive.
🔄
Framework Updates
Pilot + impact analysis first. Adoption plan. Update core libs once all teams ready.
📄 Beyond Testing: Other Uses
📦
Environment Setup
Auto-create test data, cleanup logs. Saves time, ensures proper setup.
📅
Data Aging
Manipulate date fields in DBs to keep test data current from year perspective.
📸
Screenshots & Video
Usage screenshots for release docs, marketing videos from actual system use.

💡 The ISTQB Pattern for Ch.8

If automation is slow/unstable/hard to maintain, ISTQB wants you to: improve architecture, improve test data management, improve process integration. Not: add more tests, buy another tool, increase execution frequency.

🎯 Key Takeaway

Ch.8 is 30% of your points. Even if you struggle here, banking Ch.6 and Ch.7 can still get you to the pass line.
