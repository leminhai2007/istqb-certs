Ch.1 — Introduction to Test Automation
3 pts (7%) Easy · All K2 3 Questions
✅ Benefits
🚀
More Tests Per Build
Far more than any manual team could run
⚡
Faster Execution
Tests run consistently at machine speed
🔄
Consistency
Same steps, same way — every single time
🎯
Early Feedback
Catch issues sooner, improve reliability
💥
Impossible Tests
Parallel execution, timing-critical, remote setups
🤖
Complex Scenarios
Manageable scenarios that would tie teams in knots
⚠ Challenges & Limits
💰
High Upfront Cost
Licenses, infra, training, hiring
🔧
Ongoing Maintenance
Frameworks don't maintain themselves
🔍
Programmed Only
Only checks what's explicitly coded — won't catch unexpected issues
🚫
Can't Automate Everything
Some manual tests have no effective automation path
📐 Dev Models
📐
Waterfall
Sequential phases. Automation enters late. Automation enters during/after dev. Tests run in dedicated testing phase. Limited scope vs Agile.
📑
V-Model
Dev + Test paired per level. Frameworks encouraged. Each dev stage maps to a test level: Component → Integration → System → Acceptance. Frameworks at each level.
🚀
Agile
In-sprint automation, CI/CD, cross-role collaboration. Richest opportunities. Teams define automation goals alongside business priorities. Best environment for automation.
🔧 Tool Selection
🎯 Start with what you're testing and goals
👥 Match to team skills — low-code if less technical
📈 Think long-term: scale, cost, SUT type alignment

👁 Designing for Testability
👁
Observability
Interfaces to peek inside & verify results Expose internal state so test cases can check actual vs expected outcomes. Without it, you can't confirm correctness.
🔧
Controllability
Interfaces to interact & trigger actions UI elements, function calls, TCP/IP, USB, electronic signals. Without controllability, you can't drive tests.
📜

Ch.3 — Test Automation Architecture
10 pts (23%) K3 · Precision Required 6 Questions

⚠ Every word matters

Short chapter but every distinction is exam-critical. Precision is key — don't skim.
💾 Test Automation Architecture (gTAA)
💻
SUT Interface
Connection between the SUT and the framework
📊
Project Mgmt Interface
Tracks the test automation development progress
📋
Test Mgmt Interface
Maps test case definitions to automated test cases
⚙
Config Mgmt Interface
CI/CD pipelines, environments & testware
Blueprint of your automation
The gTAA is the blueprint for how automated tests connect to the SUT, project management, test management, and configuration management (CI/CD pipelines, environments, testware).
🔧 Core Capabilities
🧪
Test Generation
Auto-generate tests from a model — optional
📄
Test Definition
Define & implement test cases & suites, separated from the SUT
🚀
Test Execution
Run tests automatically + logging & reporting
🔗
Test Adaptation
Adaptors to connect to the SUT via APIs, protocols, services
Generate → Define → Execute → Adapt
Identify which of these capabilities each tool provides, then select tooling that covers all four. Generation is optional — it comes from model-based testing.
🏗 Framework Layers
📌 Test Scripts (Top)
Actual test cases — call business logic, never jump to core libraries
🔧 Business Logic (Middle)
System-specific code, configs, app connections
📦 Core Libraries (Bottom)
Reusable code — shared across teams & apps
Why layers matter
Reuse core libs across projects, enforce separation of concerns, reduce long-term costs.
⚙ Automation Approaches
🎥
Capture/Playback
Record clicks. Quick demos only.
📄
Linear Scripting
Step-by-step. Small projects.
🛠
Structured
Reusable components. Most common.
🔄
TDD
Tests first. Red-Green-Refactor.
📊
Data-Driven
Same test, different data sets.
🔑
Keyword-Driven
Keyword tables. Non-tech friendly.
🤝
BDD
Given-When-Then. Collab.
Quick ID tips
Reuse test logic = modular. External data = data-driven. Non-tech keywords = keyword-driven.
💡 Design Principles
💡
OOP Principles
🔒Encapsulation
Hide internals
👁Abstraction
Expose only essentials
🔁Inheritance
Reuse via class hierarchy
🔄Polymorphism
Same interface, many forms
🛠
SOLID Principles
🔧Single Responsibility
📐Open-Closed
🗎Liskov Substitution
📋Interface Segregation
🗫Dependency Inversion
Better code, better tests
OOP and SOLID principles improve code readability, maintainability, and scalability — exactly like in regular software development.
🛠 Design Patterns
🚯
Facade
Hide complexity, show only what testers need
🔒
Singleton
One connection to system at a time
🏠
Page Object Model
All page info in one place — update once
🔄
Flow Model
Layer above POM for reusability
⚠ Common Exam Traps
Correct, wrong layer
Valid answer but belongs to a different framework layer. ISTQB is strict about layer responsibility.
Practical but breaks maintainability
Mirrors real practice but violates ISTQB principles. Prioritize long-term cost reduction.
Tool-first thinking
Focuses on tools not architecture. ISTQB prefers tool-agnostic design with defined interfaces.
Best vs works
Multiple answers work, only one is best. Choose scalability, modifiability, reusability.
Elimination checklist
When stuck: (1) Separates concerns? (2) Reduces maintenance? (3) Scales? (4) Fits team? (5) Avoids lock-in? Eliminate if fails 2+.

Ch.7 — Verifying the Test Automation Solution
8 pts (19%) Mostly K2 6 Questions
🔍 Core Concept: Testing the Tests
Your automation solution itself needs verification. If automation doesn't work correctly, it can't be trusted to verify anything else.
⚖ Setup & Repeatability
✅Automated install from repo > manual setup
✅Consistent versions & config across environments
✅Rebuilding produces identical results everywhere
✅Systematic setup & teardown approach
✅ What to Verify
⚡
Functional
Do components work correctly?
📈
Non-Functional
Performance, memory, interoperability
📝
Accuracy
Logs & reports reflect reality
📋 Test Suite Checks
✅
Completeness
All tests have expected results, test data present, correct SUT version
🔄
Repeatability
Same test = same result every time. Remove flaky tests from active suite.
⚠ Watch Out
💥
Tool Intrusiveness
Automation can change system behavior — false failures drop confidence
📝
Static Analysis
Test code can have security bugs too (e.g. plaintext passwords in scripts)
Ch.8 — Continuous Improvement
13 pts (30%!) 🏆 K3/K4 · Largest Chapter 6 Questions

🎯 Don't treat as optional

13 of 66 points. You may reach this chapter needing 3+ pts to pass. Master it.
📈 Finding Improvements via Data
📊Histograms reveal trends, flaky tests, error patterns
📊Use data to select tests for refactoring
📊Rethink implementations that aren't working
🤖 AI Self-Healing Tests
🤖
How It Works
UI locators as inputs → detect change → ML + image recognition → auto-fix → report changes
✅
Benefit
Speeds up maintenance — version control & code updates happen faster
💡 Wait Mechanisms (Worst → Best)
🗑
1. Hard-coded
Wait X ms. Unpredictable. Fragile. Response times vary. Too short = fail. Too long = waste. Unreliable.
🔄
2. Polling
Check state periodically. Include timeouts! Waits only as long as needed. Much better but can miss race conditions.
⭐
3. Event Subscription
React to system events. Most reliable. Needs event support in language & system. Reacts to actual changes. Still needs timeouts.
⚙ Scripting & Execution Improvements
🛠Upgrade: linear → data-driven or keyword-driven
📦Consolidate overlapping tests into reusable functions
📂Failure recovery: continue with next test, reboot if needed
⚙Optimize: parallel execution, split suites, remove duplicates
📅Schedule jobs at specific times to reduce manual intervention
🛠 Architecture & Framework Updates
🏗Refactor automation when SUT provides new test APIs
📦Core library updates: pilot first → adoption plan → update deps
📂Move repeated actions into setup/teardown methods
📝 Beyond Testing
🌐
Environment Setup
Auto-create test data, cleanup environments
📅
Data Aging
Update date fields to keep them current
📸
Screenshots/Video
Release docs, marketing, usage examples

🎯 ISTQB Pattern for Ch.8

If automation is slow/unstable/hard to maintain → improve architecture, test data management, or process integration.
NOT: add more tests, buy another tool, or increase execution frequency.
