Ch.1 — Fundamentals of Testing
8 pts (20%) Mostly K1/K2 8 Questions
📝 What Testing Is
✅
Testing IS
Checking software by running it or reviewing work products, comparing actual vs expected, learning how the product behaves
🚫
Testing IS NOT
Proof that there are zero defects. It reduces risk and finds problems. Debugging (fixing defects) is separate.
💡 Key Terms
📌Test objectives — why you test
📦Testware — artifacts: plans, cases, data, reports
👥Roles — who does what in a team
⚡ Why Organisations Test
💰Failures cost money, reputation, and safety
✅Supports confidence in releases, compliance, contracts
📈Inform go/no-go decisions
Causes vs purpose
Questions often contrast causes of defects (human error, complexity, time pressure) with why we test (find defects, build trust, inform decisions).
📚 Seven Testing Principles
🔍
Shows Defects
Testing finds problems but cannot prove absence of all defects
📈
Exhaustive = Impossible
Use risk and priorities instead of testing everything
◀
Early Testing
Saves time — shift left mindset starts here
📊
Defect Clustering
A few modules hold most bugs (Pareto 80/20)
💧
Pesticide Paradox
Same tests stop finding new issues — review & update regularly
🌐
Context Matters
Safety-critical vs internal tool — different approaches

⚠ Absence-of-Errors Fallacy

Finding and fixing all defects does not mean the system is useful. A bug-free product that does not meet user needs still fails.

Ch.2 — Testing Throughout the SDLC
6 pts (15%) K1/K2 6 Questions
📐 Lifecycle Models
📐
Sequential
Testing in defined phases after dev milestones
Details
Waterfall: testing happens after development. Linear, documentation-heavy. Limited feedback loops.
🔄
Iterative
Testing repeats every sprint or increment
Details
Each iteration produces a working slice. Testing happens continuously within each cycle. Faster feedback.
🚀
Agile / DevOps
Whole-team quality, CI/CD, automated checks
Details
Agile: fast feedback, working software, cross-role collaboration. DevOps adds continuous integration, delivery, and pipeline automation.
📌 Test Levels
👤 Acceptance
Validate fitness for use — users or business reps involved
💻 System
Whole product behaviour end to end
🔗 Integration
Interfaces between components or systems
🔧 Component (Unit)
Small pieces, stubs/drivers, usually developers
Levels vs Types
Test levels = how much is integrated (component → system). Test types = what quality aspect you check (functional, performance, etc.). Do not confuse them.
📌 Test Types
✅
Functional
What the system does
📈
Non-Functional
How well (performance, usability, security)
🔄
Regression
Changes did not break existing behaviour
✓
Confirmation
A specific fix works correctly
🔧 Maintenance Testing
🔄Happens after release: fix, migrate, or retire software
📈Impact analysis decides how much to retest
Ch.3 — Static Testing
4 pts (10%) K1/K2 · Easy Points 4 Questions

🎯 Don't skip this

Only 4 questions but they are often "free" points. Small chapter, easy marks.
🔍 Static vs Dynamic
📄
Static Testing
Examines work products without executing code: requirements, designs, code reviews, checklists
✅Find defects early, cheap feedback
✅Improved communication
🚫Cannot catch runtime/timing bugs
▶
Dynamic Testing
Requires running the software to observe behaviour
✅Catches runtime issues
✅Environment & timing problems
🚫More expensive, later in lifecycle
👥 Review Types (by formality)
💬
Informal
Ad-hoc, least formal
➔
📝
Walkthrough
Author-led, team review
➔
🔍
Technical Review
Peer review by experts
➔
📝
Inspection
Most formal, data-driven
👥 Review Roles
✍
Author

🎯
Moderator

🔍
Reviewer

📝

Ch.4 — Test Analysis and Design
11 pts (27.5%) K2 + K3 · Biggest Chapter 11 Questions

🔥 Half the exam weight

This is the biggest chapter. Technique questions dominate. Practice picking the right technique until it feels automatic.
🎯 Choosing a Technique
📝Techniques derive tests from: requirements, risks, structure, experience, or collaboration
💡Exams love: "given this input domain / code / story, which technique fits best?"
📝 Black-Box Techniques
📊
Equivalence Partitioning
Split inputs into classes that should behave the same
Example
Age 0–15 = child, 16–64 = adult, 65+ = senior. One test per partition = efficient coverage.
◀
Boundary Value Analysis
Test edges of partitions (2-value and 3-value BVA)
Example
For range 1–100: test 0, 1, 2, 99, 100, 101. Most defects hide at boundaries.
📋
Decision Table Testing
Rules with combinations of conditions and actions
Example
IF login valid AND 2FA on THEN redirect to dashboard. Each rule = one test case. Handles complex logic.
🔄
State Transition Testing
Valid states and transitions (tables or diagrams)
Example
Login: Logged Out → (valid creds) → Logged In → (timeout) → Session Expired. Test valid + invalid transitions.
👤
Use Case Testing
Flows through user goals (happy path + alternatives)
Example
E-commerce: browse → add to cart → checkout → payment. Include alternate flows like "out of stock".

📊 K3 Tip

K3 items often ask how many test cases a technique produces. Work through numeric examples until automatic.
🔧 White-Box Techniques
📄
Statement Coverage
Execute every line of code at least once
📋
Branch/Decision Coverage
Every true/false branch taken at least once
Coverage caveat
Coverage is a measure, not a goal by itself. 100% statement coverage does not mean zero defects.
🤖 Experience-Based
🔍
Exploratory Testing
Learn and test at the same time — charter-based sessions
💡
Error Guessing
Target likely failures based on experience
🤝 Collaboration-Based
👥Write tests from user stories with the team
📝ATDD/BDD style conversations (Given-When-Then)
📋Checklist-driven sessions
ATDD focus
Who collaborates, what artifact you start from, and what you produce: examples, scenarios, concrete tests.
Ch.5 — Managing the Test Activities
9 pts (22.5%) K2 + K3 9 Questions

⚠ Pass/fail chapter

Seven or more correct here often decides pass vs fail. Combined with Ch.1–4, target 31–33 pts before this.
📝 Test Planning
📝A test plan covers: scope, approach, resources, schedule, entry/exit criteria
🎯Aligns testing with project constraints
⚠ Risk-Based Testing
💥
Product Risk
What can fail for users — quality aspects, usability, performance
⏰
Project Risk
Can we deliver on time — resources, scope, deadlines
Priority principle
Risk-based testing prioritises effort where product and project risks are highest. More risk = more testing.
📈 Monitoring & Control
📊
Monitor
Tests run, pass/fail, coverage, defects
➔
📈
Compare
Actual vs planned progress
➔
🛠
Control
Re-prioritise, add resources, narrow scope, escalate
📂 Configuration Management
📦Keeps testware aligned with what you are testing
📄Version control, baselines, traceability
🐛 Defect Management
1. Log Report
Clear title, steps, expected vs actual, environment
2. Triage
Assign severity & priority
3. Track to Closure
Fix, verify, close the defect
4. Analyse Trends
Use data for process improvement
📝 Defect Report Essentials
📝
Clear Title
Summary that identifies the problem
📝
Steps to Reproduce
Exact actions someone can follow
📋
Expected vs Actual
What should happen vs what did happen
💻
Environment
OS, browser, version, test data used

✅ Benefits vs Risks
🚀
Benefits
✅Faster regression, more runs
✅Fewer human slips on repetitive checks
✅Consistency, speed, repeatability
⚠
Risks
🚫Unrealistic expectations
🚫High maintenance burden
🚫False confidence, tool mismatch
🚫Neglect of exploratory work
Key principle
Tools are not magic. They support the test strategy you already chose. Still need skilled people, maintenance, and lifecycle integration.
